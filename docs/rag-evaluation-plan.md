# Roadie evaluation: current pipeline versus fine-tuned LLM

Agreed direction, 4 November 2026: the current working pipeline is the baseline.
Compare it with the fine-tuned LLM; a retrieval ablation is not the primary experiment.
This document is a design, not a completed evaluation or a frozen baseline release.

The supervisor's exact requirements are not yet known. Use the published RAGAS
paper for the framework's academic basis and versioned library documentation for
the selected implementations; do not imply that all modern metrics originated
in that paper or that using RAGAS guarantees university approval.

Begin with a diagnostic development evaluation of the current pipeline. Use its
failures to decide whether fine-tuning is warranted and which behaviours need
training. No fine-tuning target or training dataset has been selected yet. Any
cases whose outputs influence those decisions belong to development, not the
fresh final test set. Reserve a final test partition before training starts.

## Comparison

The user confirmed that every application LLM call uses the same model, including
intent analysis and answer generation. The baseline uses the current model at all
such call sites; the tuned condition uses the fine-tuned model at all such call
sites. The primary experiment is therefore an end-to-end pipeline comparison.

Run the same test inputs and initial vehicle/conversation state through each
condition independently. Keep source documents, retrieval algorithms, embedding
and reranking models, filters, context budgets, prompts and decoding settings fixed
where supported. Allow the changed LLM to produce different intents, routes, search
queries, selected evidence and answers. Capture these differences; do not force
baseline contexts into the tuned pipeline for the primary experiment. Retrieval
scores may change through LLM-driven query and route changes even though retrieval
code is unchanged. Evaluate final user-visible answers after the same validation
and formatting path, retaining raw outputs and traces for diagnosis.

Audit all application LLM call sites before running the comparison, including
offline preparation, image descriptions and optional fallbacks. Freeze existing
prepared/indexed artifacts for the primary online-pipeline experiment and record
their generating model where known. This is shared baseline preparation, not a
claim that those artifacts were regenerated by the tuned model. Any new LLM work
in a condition must use that condition's model. If comparing preparation too,
rebuild separate artifacts from identical originals for each condition and report
that as a broader experiment without overwriting the baseline corpus.

Sequential conversation tests use each condition's own previous answers and may
diverge; distinguish these from fixed-history paired tests. Deterministic emergency
responses that bypass the model are system checks, not evidence of fine-tuning
improvement. Fixed-context answer replay is optional diagnostic work only.

The RAGAS evaluator is measurement infrastructure, separate from application LLM
calls. Keep its model, prompts and settings identical for both conditions; do not
switch or fine-tune the judge alongside the system being evaluated.

Record the base-model identity before training. If the tuned model derives from a
different model than the current baseline, include that model's untuned version
as a third condition to isolate the effect of training from a model substitution.

Before the baseline run, preserve the full runnable working source (including
uncommitted/untracked changes), dependency versions, non-secret configuration,
document revisions/hashes, prompts, dataset, judge settings and evidence. The
existing recovery baseline predates subsequent fixes and is not this experiment's
baseline. Do not rely on a Git commit ID alone for the currently dirty workspace.

- Published learning guides covering tyres, fluids, wipers, batteries, warning

does not establish performance over the entire vehicle catalogue.

## Question authoring and separation from training

1. Use existing recovery questions as development/regression cases. Previously
   inspected cases, even those named heldout, are not automatically a fresh test set.
2. Build a source-section and user-task coverage map before querying the chatbot.
3. Draft questions and factual reference answers from complete source sections,
   independently of baseline answers and retrieved results. Preserve relevant
   headings, conditions, units, table footnotes and variant restrictions.
4. Attach source IDs, revisions, PDF page numbers (and printed labels if different),
   element IDs and supporting excerpts to each reference. Allow equivalent evidence
   where duplicate or overlapping sources support the same fact.
5. Include natural novice wording, informal English and supported mixed-language
   inputs. Preserve required output-language behaviour. Include ambiguity, missing
   evidence and multi-source cases; do not merely paraphrase manual headings.
6. Group cases by underlying scenario/fact set before splitting train/development/
   test. Keep paraphrases and equivalent answers out of separate splits. Existing
   training data must be checked against this partition before the test is frozen.
7. Review answerability and references against originals. AI-drafted references
   remain draft until reviewed; record who reviewed what and when. Review critical
   claims with a suitable human reviewer. Do not describe AI checking as human review.
8. Freeze test cases before model selection or final evaluation. Use development
   data for training decisions and judge calibration; evaluate the test set only
   after those decisions are fixed.

The manuals remain in the RAG corpus for both models: access to test-question
evidence through retrieval is intended. Test questions, answers and near-duplicates
must not enter fine-tuning or validation data. To claim generalisation to unseen
documents, reserve entire documents/vehicles from training as a separate experiment.

## Practical initial size

First prepare five development smoke cases to check evidence capture and scoring.
Then target 50 fresh final cases, subject to source review:

| Primary category | Cases |
| --- | ---: |
| Vehicle-specific manual questions, balanced across the two vehicles | 20 |
| General learning-guide questions | 12 |
| Questions requiring evidence from multiple sources | 8 |
| Clarification, unsupported requests, vehicle conflicts and emergency behaviour | 10 |

Tag secondary properties separately: informal wording, language, numerical value,
table/image dependence, safety relevance and number of evidence sources. Add a
small separately reported multi-turn regression suite. Fifty cases are a practical
scope choice, not a statistical guarantee or RAGAS requirement.

Each case needs: ID, split, scenario group, input, vehicle scope, history, category,
expected route/behaviour, factual reference, required facts, prohibited claims,
source provenance, metric eligibility, reviewer status and version. Behaviour-only
cases need a rubric rather than an invented factual reference.

## Scoring and reporting

Use Context Precision and Recall on each condition's actual retrieved evidence;
Faithfulness and Factual Correctness (F1) for eligible generated answers; and Answer
Relevancy as an additional responsiveness measure. Pin exact implementations,
package versions, evaluator model, embeddings and metric settings after a smoke
test. Keep the judge identical across both conditions and blind condition labels
during human review. RAGAS supports synthetic generation, but it is optional:
reviewed manually/AI-assisted authored questions can use the same scoring metrics.

Text-only judges do not see original image/table pixels. Flag such cases and
review them separately unless a suitable multimodal evaluator is validated.
Do not claim missing textual support proves a visual claim is hallucinated.
Keep instructions and generated descriptions distinct from authoritative evidence.

Report paired score changes, distributions, category counts, evaluation coverage,
missing/error rates and concrete failures. Treat undefined metrics as inapplicable,
not zero. Include human checks of vehicle applicability, required facts, numerical
values/units, unsupported claims, appropriate refusal and citations/media. Preselect
a review subset plus all critical failures. Estimate uncertainty at scenario-group
level if reporting confidence intervals; do not treat paraphrases as independent.

## Initial implementation status

The first five draft development cases and review sheet are local artifacts:
`output/evaluations/ragas-preparation/development-smoke-v1.jsonl` and
`output/evaluations/ragas-preparation/review-first-five.md`. The user accepted the
complete review sheet on 4 November 2026. The original draft and exact acceptance
message are retained locally; this is user review, not automotive expert validation.
DEV002 retains a disclosed manual edition/applicability note: the catalogue
assigns the 2021-current Myvi manual, while its relevant page has a 2022 footer.

`scripts/evaluate_rag.py` validates the dataset and source hashes, then captures
the actual query pipeline in an isolated serial process. Evaluation-only wrappers
in `scripts/evaluation_capture.py` record intent, all answer attempts, exact packed
contexts, prompts, schemas, actual supplied images (saved by hash), model IDs,
raw results and which attempt contributed the returned answer. The existing admin
trace remains a bounded candidate diagnostic; it is not a complete retrieval-stage
export. Captured generation input records contain the eligible pre-packing records.

Validate with no application/model calls:

```sh
python3 -m scripts.evaluate_rag --dataset output/evaluations/ragas-preparation/development-smoke-v1.jsonl --validate-only
```

To make a deliberately draft development capture, use the project's environment:

```sh
.venv/bin/python -m scripts.evaluate_rag --dataset output/evaluations/ragas-preparation/development-smoke-v1.jsonl --output output/evaluations/ragas/development-capture-01 --allow-draft
```

Capture runs require a new output directory, preserve source snapshots and installed
package versions, and never write credentials to the manifest. They verify saved
scope revisions strictly but do not refresh live publication status. They are
initial diagnostic tooling, not yet the frozen final experiment.

The approved five-case diagnostic run is now captured at
`output/evaluations/ragas/development-baseline-02/`. Every application LLM call
used `gemini-3.5-flash-lite`; the clarification case used the deterministic
safeguard without a model call. The application environment remains unchanged.

RAGAS 0.4.3 is installed separately in `output/evaluations/ragas-env/` using
`requirements-evaluation.txt`; the resolved environment is recorded locally.
RAGAS can evaluate this custom pipeline without the application using LangChain.
Its own LangChain dependencies are pinned for compatibility with its imports.

`scripts/score_rag.py` scores saved outputs with the library's collections metrics.
`scripts/ragas_gemini.py` supplies a neutral Google Interactions judge through
RAGAS's modern structured-LLM interface; it does not change metric prompts,
calculations or Roadie's generation settings. The transport uses the SDK's
`output_text` property. Judge responses are cached per case/metric/prompt/schema
and occurrence, preserving three separate relevance-question generations.
Scored metrics resume from saved results; errors are distinct from zero scores.

The judge is fixed at `gemini-3.5-flash-lite` for this pilot. Answer Relevancy uses
`gemini-embedding-001`, `SEMANTIC_SIMILARITY`, one text per request, with the Cloud
v1 endpoint in `us-central1`. This embedding endpoint is configured independently
of the judge's global Interactions endpoint. Future comparisons must retain these
choices or explicitly rerun both conditions under the new evaluator configuration.

The final successful pilot scores are in `scoring-v4/`: all 20 applicable
case/metric pairs scored without errors, and five metric entries are N/A for the
clarification case. Earlier sandbox, SDK-adapter and embedding-endpoint failures
are retained separately and excluded. Compatible cached judge responses were
reused during endpoint repair, with provenance recorded; chatbot answers were
not regenerated for scoring retries.

| Metric | Pilot mean | Scored cases |
| --- | ---: | ---: |
| Context Precision | 0.654 | 4 |
| Context Recall | 0.813 | 4 |
| Faithfulness | 0.625 | 4 |
| Factual Correctness (F1; high atomicity/coverage) | 0.535 | 4 |
| Answer Relevancy (strictness 3) | 0.884 | 4 |

These are small development-sample means, not system accuracy or universal pass
scores. Reference agreement can penalise correct additional facts absent from
the reviewed reference. Text faithfulness can penalise permitted general-information
claims and cannot validate pixels. The same-family judge can share generator
errors; its verdicts require inspection rather than blind acceptance.

Source inspection found an applicability failure in DEV001: the washer answer
borrowed a dirty-fluid service-centre instruction from the automatic-transmission
section (Alza PDF page 200, printed 14-18). The retrieved generic CAUTION heading
obscured that context. This illustrates a source/chunk-context failure that model
fine-tuning alone should not be assumed to solve. DEV005 matched the clarification
rubric in this example. These annotations are explicitly AI-assisted inspection.

`scripts/report_rag.py` produces the local HTML, Markdown and CSV report in
`output/evaluations/ragas/development-baseline-02/report/`, including actual answers,
references, supplied contexts, counts, configuration and inspection notes. Source
snapshots, original-pixel inputs, per-claim judge responses and dependency versions
remain available for audit. A baseline-versus-tuned comparison report, full candidate
stage export and a broader reviewed dataset remain future work.

## Pipeline fixes after the first pilot

The preserved `development-baseline-02` remains the original comparator. Changes
to retrieval and answer generation are a separate pipeline experiment, before
any model fine-tuning. The approved questions, references and evaluator settings
remain fixed for this development comparison.

- Manual retrieval keeps broad hybrid candidates. Explicit separate questions
  also receive individual scoped searches, with rank fusion and deduplication.
  Their best evidence is represented during the final joint text reranking.
- Manual and published-guide prose are reranked together before the final text
  budget. Visual selection remains independently bounded. Failed reranking falls
  back to available hybrid order, with a diagnostic rather than an empty answer.
- Generic warning/note passages can acquire literal preceding OCR blocks only
  after a unique complete-text match on the same PDF page and column. Context is
  bounded, stops at a substantive heading and records OCR hashes/indices. No
  heading parentage is inferred from PDF reading order. Missing or ambiguous
  provenance leaves the passage unchanged. Original chunks/index are unchanged.
- The writing prompt stresses component/action applicability and requested facts.
  A bounded evidence-review pass then edits factual answers against the supplied
  evidence and its own citations before existing integrity validation. This uses
  the same application model as intent and drafting, with one extra call per
  successful factual answer in this pilot. `RAG_GROUNDING_REVIEW=false` disables
  the pass for an explicitly configured experiment. Review failure surfaces as a
  generation failure; unchecked output is not silently substituted.

`development-pipeline-fixes-01` was a blocked sandbox attempt and was stopped.
`-02` and `-03` are exploratory captures retained to show the persistent errors
that motivated better context boundaries, separate question retrieval and the
evidence review. `development-pipeline-fixes-04` captures the implemented pipeline
with the evidence review enabled. Its means were 0.821 precision, 1.000 recall,
1.000 faithfulness, 0.730 factual F1 and 0.865 relevance. The remaining omissions
and unnecessary details motivated an explicit source-fact checklist in the review.

The implemented final version is captured in `development-pipeline-fixes-05/`.
The checklist and the answer are retained in the captured review response. The
report in its `report/` directory compares the following means with the original
baseline, using the same dataset hash and identical evaluator configuration:

| Metric | Original baseline | Pipeline fixes | Scored cases |
| --- | ---: | ---: | ---: |
| Context Precision | 0.654 | 0.821 | 4 |
| Context Recall | 0.813 | 1.000 | 4 |
| Faithfulness | 0.625 | 1.000 | 4 |
| Factual Correctness F1 | 0.535 | 0.775 | 4 |
| Answer Relevancy | 0.884 | 0.890 | 4 |

All 20 applicable metric entries scored without errors; the five clarification
entries remain N/A. There are 12 successful application LLM calls (intent, draft
and evidence review for each factual answer), all using `gemini-3.5-flash-lite`.
The clarification case uses none. These measurements are development results
after iterating on the same questions, not an estimate of performance on new
questions. Original references were not rewritten to fit the answers.

All five means exceed the project's proposed 0.75 target, but individual results
do not: DEV001 context precision is 0.450 and DEV004 factual F1 is 0.500. The oil
answer still omits level-ground preparation, and the maintenance answer omits
checking the applicable item's last service date and mileage. A source checklist
and an automated faithfulness score of 1.000 do not guarantee completeness or
expert-verified automotive correctness. Broader reviewed development cases and a
fresh final holdout are still required. All exploratory captures remain available.

Validation: 67 targeted application/capture/scoring tests and two pinned-judge
adapter tests pass. The comparison report checks evaluator configuration and
dataset equality and records case counts, N/A entries and errors. The extra
review call adds cost and latency; the cold first-case timing is not a controlled
performance benchmark.

Before comparing original and fine-tuned models, freeze whichever pipeline is
selected and use it for both models, including its evidence-review call. Keep the
RAGAS judge fixed. Do not attribute pipeline fixes to model fine-tuning.
