# car-maintenance-v3
Latest version of FYP, focus on RAG pipeline only

# RAG Pipeline: Stage 1 — Parsing

Stage 1 ingests finalized Markdown manual files, converts them to structured HTML, and parses them into hierarchical `HTMLNode` trees serialized as JSON.

> **Note:** OCR processing happens upstream and is out of scope for this stage.

---

## Directory Layout

```text
rag_project/
├── data/markdown/         # Input: Raw .md files (e.g., axia-2023.md)
└── output/parse/          # Output: Generated .html and _html_tree.json files

```

---

## Core Components

* **`app/models/html_node.py`**
Defines the `HTMLNode` schema. Captures document context, tag hierarchies, text content, parent-child relationships, depth, and source position.
* **`app/parsing/markdown_parser.py`**
Handles the core Markdown-to-HTML transformation.
* **`app/parsing/html_tree.py`**
Parses raw HTML into a structured `HTMLNode` object model while preserving heading hierarchy and metadata.
* **`scripts/run_parsing.py`**
Executes the HTML-to-`HTMLNode` JSON conversion stage.

---

## Running the Parsing Stage

Place your target Markdown files in `data/markdown/`, then execute the following from the project root:

**Step 1: Convert Markdown to HTML**

```bash
python -m app.parsing.markdown_parser

```

*Reads from `data/markdown/*.md` and writes intermediate `.html` files to `output/parse/`.*

**Step 2: Convert HTML to HTMLNode JSON**

```bash
python -m scripts.run_parsing

```

*Reads `.html` files from `output/parse/` and outputs `<document_name>_html_tree.json` (consumed by **Stage 2: Normalization**).*

> ⚠️ **Order Matters:** Step 1 must be run before Step 2. `run_parsing.py` expects the raw HTML files to already exist in `output/parse/`.

---

## Planned Architecture Refactor

Currently, Stage 1 requires running two separate commands. The target design is to have `scripts/run_parsing.py` orchestrate both steps internally:

```bash
python -m scripts.run_parsing
# Target execution flow: Markdown -> HTML -> HTMLNode JSON

```

*`markdown_parser.py` will remain a reusable module inside `app/parsing/`, but `run_parsing.py` will serve as the single CLI entry point for the stage.*

---

## Dependencies

Ensure the following are included in your `requirements.txt`:

* `mistletoe`
* `beautifulsoup4`

# RAG Pipeline: Stage 2 — Normalization

Stage 2 converts the `HTMLNode` trees produced by Stage 1 into a semantic node tree.

The purpose of this stage is to translate raw HTML structure into meaningful document elements such as `Document`, `Section`, `Paragraph`, `Table`, `Image`, and `List`.

The normalized tree is serialized as JSON and becomes the input for the database stage.

> **Note:** Supabase is not involved in this stage. Database-generated UUIDs are assigned later during database import.

---

## Directory Layout

```text
rag_project/
├── output/parse/          # Input: HTMLNode JSON from Stage 1
│
└── output/nodes/          # Output: Normalized semantic node JSON

```

---

## Core Components

* **`app/models/metadata.py`**
Defines the metadata attached to each semantic node. Metadata currently includes:
* `document_name`
* `source_tag`
* `source_depth`
* `source_position`
*Database-specific fields such as the final UUID and `parent_id` are handled later by the database stage.*


* **`app/models/node.py`**
Defines the semantic node types and their tree relationships. Supported node types currently include:
* `Document`
* `Section`
* `Paragraph`
* `Table`
* `Row`
* `Cell`
* `Image`
* `List`
* `ListItem`


* **`app/normalization/converters.py`**
Converts individual `HTMLNode` objects into their corresponding semantic node types.
* **`app/normalization/builder.py`**
Builds the complete semantic tree by recursively processing the HTMLNode tree and connecting semantic parent-child relationships.
* **`scripts/run_normalize.py`**
Runs the normalization stage for all HTMLNode JSON files in `output/parse/`.

---

## Running the Normalization Stage

Stage 2 expects the HTMLNode JSON files generated by Stage 1 to already exist in `output/parse/`.

From the project root, run:

```bash
python -m scripts.run_normalize

```

The script:

1. Reads every `.json` file from `output/parse/`.
2. Converts each HTMLNode tree into a semantic node tree.
3. Attaches the document name to every node's metadata.
4. Writes the normalized node tree to `output/nodes/`.

For example:

```text
output/parse/
└── axia-2023_html_tree.json
          ↓
output/nodes/
└── axia-2023_html_tree.json

```

Each output file contains the complete semantic hierarchy and can be inspected before continuing to the database stage.

---

## Important Design Decisions

### Document Name

Every semantic node carries the document name in its metadata. This allows document identity to remain available throughout later stages, including chunking.

### Parent-Child Relationships

The normalized JSON represents the hierarchy directly through nested `children`. The normalization stage does not assign database IDs or database `parent_id` values. Supabase generates the final UUIDs during the database import stage.

### Unstructured Documents

The normalization stage does not require every document to have a perfect heading hierarchy.

A structured document may produce:

```text
Document
└── Section
    ├── Paragraph
    └── Table

```

An unstructured document may simply produce:

```text
Document
├── Paragraph
├── Paragraph
├── Table
└── Paragraph

```

Both are valid semantic trees. The normalization stage should preserve structure that exists rather than inventing sections that are not present in the source.

---

## Output

The normalized JSON is a checkpoint for inspecting the semantic structure before database insertion.

The pipeline currently follows:

```text
Markdown
    ↓
HTML
    ↓
HTMLNode JSON
    ↓
Semantic Node JSON
    ↓
Database

```
# Stage 3 — Database Ingestion

Stage 3 imports the normalized semantic node trees from Stage 2 into Supabase/PostgreSQL. 

It persists the document hierarchy in a relational table using foreign keys (`parent_id`), allowing full tree reconstruction during retrieval.

> **Note:** Database UUIDs are generated dynamically by Supabase upon insert. The normalization stage does not generate or depend on DB UUIDs.

---

## Directory Layout

```text
rag_project/
├── app/database/          # Schema models, Supabase client, and importer logic
├── output/nodes/          # Input: Normalized JSON trees from Stage 2
└── output/database/       # Output: Ingestion execution checkpoints

```

---

## Core Components

* **`app/database/models.py`**
Defines Pydantic representations (`DocumentNodeCreate` for inserts, `DocumentNode` for DB retrieval with runtime `children` mapping).
* **`app/database/client.py`**
Initializes the Supabase client instance using environment variables.
* **`app/database/importer.py`**
Handles document validation, existing record deletion, top-down tree insertion, UUID resolution for parent-child links, and local checkpoint export.
* **`scripts/run_import.py`**
Stage 3 runner. Iterates through `output/nodes/*.json` and executes the import pipeline.

---
``

## Schema & Indexing

All nodes reside in a single self-referential table (`document_nodes`):

* **Primary Key:** `id` (`uuid`, default `gen_random_uuid()`)
* **Foreign Key:** `parent_id` (`uuid`, references `document_nodes(id)` `ON DELETE CASCADE`)
* **Indexes:** `document_name` (fast document lookup), `parent_id` (fast child node retrieval)

---

## Running the Database Stage

Ensure normalized JSON trees exist in `output/nodes/`, then execute:

```bash
python -m scripts.run_import

```

### Execution Flow

1. **Idempotent Clean Step:** Existing records matching `document_name` are deleted (cascading to all children).
2. **Top-Down Insertion:** Root nodes insert first $\rightarrow$ Supabase returns generated UUIDs $\rightarrow$ UUIDs bind as `parent_id` for recursive child inserts.
3. **Checkpoint Generation:** Exports execution metadata and DB-persisted records to `output/database/<document_name>.json`.


# Stage 4: Retrieval

This stage retrieves document nodes from Supabase and reconstructs the original semantic tree.

## Input

The database table:

```text
public.document_nodes
```

The database contains flattened node records with `parent_id` relationships.

## Process

```text
Supabase
↓
Retrieve node records
↓
Group records by document
↓
Rebuild parent-child relationships
↓
Restore source ordering
↓
Validate hierarchy
↓
Save reconstructed trees
```

Database retrieval order is **not** assumed to represent document order.

Nodes are connected using `parent_id`, then children are sorted using `source_position`.

The reconstructed hierarchy is also checked for missing parents and cycles.

## Files

### `app/database/retriever.py`

Contains the retrieval and tree reconstruction logic.

Responsibilities:

* Retrieve nodes from Supabase.
* Group nodes by `document_name`.
* Reconstruct parent-child relationships using `parent_id`.
* Restore the original order using `source_position`.
* Validate the reconstructed hierarchy.
* Save the reconstructed tree as JSON.

### `scripts/run_retrieval.py`

Entry point for the retrieval stage.

It connects to Supabase and runs the retrieval process.

Run it from the project root:

```bash
python -m scripts.run_retrieval
```

## Output

Reconstructed document trees are saved to:

```text
output/retrieval/
```

Each document gets its own JSON file:

```text
output/retrieval/
├── document_a.json
├── document_b.json
└── ...
```

The output preserves:

* document name
* node ID
* parent ID
* node type
* source tag
* source depth
* source position
* title
* text
* image information
* table information
* child nodes

The output is a hierarchical representation reconstructed from the flat database records.

## Example

Database records:

```text
Document
├── Section
│   ├── Paragraph
│   └── Table
│       ├── Row
│       │   ├── Cell
│       │   └── Cell
│       └── Row
│           ├── Cell
│           └── Cell
```

are reconstructed into the same parent-child structure in:

```text
output/retrieval/document.json
```

This reconstructed tree is the input for the next stage, **Chunking**.


# RAG Pipeline: Stage 6 - Embedding

## Purpose

This stage converts the semantic chunks produced by Stage 5 into vector embeddings and stores them in ChromaDB for semantic retrieval.

The pipeline is:

Markdown
→ Parsing
→ Normalization
→ Database
→ Retrieval
→ Chunking
→ Embedding

OCR is handled separately and is not part of this project.

## Input

Stage 6 reads the chunk files produced by Stage 5:

```text
output/chunks/
````

Each chunk contains:

* semantic text
* document name
* section path
* node IDs
* parent information
* source information
* other metadata

The chunk text is what gets embedded. Technical metadata is stored separately.

## Embedding Model

The embedding model used is:

```text
nomic-ai/nomic-embed-text-v1.5
```

It is loaded through `sentence-transformers`.

The model requires task prefixes.

For document embeddings:

```text
search_document: <chunk text>
```

For query embeddings:

```text
search_query: <user question>
```

This distinction must be preserved.

## Embedding Dimensions

The current baseline uses the model's full:

```text
768 dimensions
```

Nomic Embed Text v1.5 supports Matryoshka dimensions such as 768, 512, 256, 128, and 64.

Dimension tuning is intentionally postponed.

## Vector Database

ChromaDB is used as the vector database.

The database uses Chroma's persistent client so that embeddings remain available after the program exits.

Storage:

```text
output/embeddings/chroma/
```

Collection:

```text
rag_chunks
```

Collection metadata records the embedding model and dimension.

## Chunk IDs

Chunks do not currently have IDs in Supabase.

Node IDs and chunk IDs are therefore treated as different concepts.

Each chunk receives a unique ID during embedding, for example:

```text
myvi-2005-owner-manual-eng_chunk_000001
myvi-2005-owner-manual-eng_chunk_000002
```

These IDs are used as Chroma IDs.

Original node IDs remain inside the chunk metadata for traceability.

A single node may contribute to multiple chunks, so a node UUID cannot be used as a chunk ID.

## Embedding Process

The stage performs:

```text
output/chunks/*.json
        ↓
load chunks
        ↓
extract chunk text
        ↓
add "search_document:" prefix
        ↓
Nomic Embed Text v1.5
        ↓
embedding vectors
        ↓
ChromaDB
```

Multiple chunk files/documents can be processed in one run.

## Project Files

The main Stage 6 files are:

```text
app/
└── embedding/
    ├── __init__.py
    ├── embedder.py
    └── vector_store.py

scripts/
└── run_embedding.py
```

### `app/embedding/embedder.py`

Responsible for loading the embedding model and generating embeddings.

It provides separate functionality for:

* document embeddings
* query embeddings

The document and query prefixes are handled here.

### `app/embedding/vector_store.py`

Responsible for interacting with ChromaDB.

It handles:

* persistent ChromaDB connection
* collection creation/access
* inserting/upserting embeddings
* storing chunk text
* storing chunk metadata
* using unique chunk IDs

### `scripts/run_embedding.py`

The stage entry point.

It loads the chunk files and sends them through the embedding process.

Run it from the project root:

```bash
python -m scripts.run_embedding
```

Do not run:

```bash
python scripts/run_embedding.py
```

## Output

Generated embedding data is stored under:

```text
output/embeddings/
```

including the persistent ChromaDB files.

These files are generated artifacts and should not normally be committed to Git.

The repository should contain the code required to recreate them.

## Current Baseline

The current chunking/embedding baseline uses approximately:

```text
Chunk size: 2000 characters
Embedding model: nomic-ai/nomic-embed-text-v1.5
Embedding dimension: 768
Vector database: ChromaDB
Collection: rag_chunks
```

The current test corpus contains approximately 891 chunks for the tested document.

These settings are intentionally frozen for now.

Do not tune the chunk size, embedding dimension, or embedding model during this stage.

A query about parking on a slope retrieved relevant results including:

* parking on a slope

Results were relevant across multiple vehicle manuals.

This confirms that the baseline embedding and vector-storage pipeline is functioning.

Formal retrieval evaluation will be performed in the next stage.

## Important Decisions

The following decisions are intentional:

* ChromaDB is used for vector storage.
* Nomic Embed Text v1.5 is used for embeddings.
* Full 768-dimensional embeddings are used initially.
* Document embeddings use `search_document:`.
* Query embeddings use `search_query:`.
* Chunk IDs are separate from database node IDs.
* Chunk metadata is stored separately from the embedding text.
* The current raw corpus is retained as the baseline.
* Markdown cleaning is postponed.
* Embedding/model tuning is postponed.
